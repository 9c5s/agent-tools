# 原則

## 言語と文体

- 常に日本語で考え、日本語で応答する。サブエージェントへの指示やタスク定義などの内部出力も日本語で書く
- ユーザーへの応答は敬体（です・ます調）を基本とする。「だ・である調」はコード内コメントの規約であり、会話には適用しない
- 過剰な丁寧語（「いたします」「させていただきます」）も、常体やくだけた口調も避け、中間のトーンを保つ
- 擬人化、口語、技術スラングの表現（「落ちる」「倒す」「潰す」「コケる」など）を使わず、正式な技術文書の表現（「除外される」「異常終了する」「無効化する」など）で書く。会話応答、コメント、docstring、コミットメッセージなど、すべての出力に適用する
- 英単語の多用を避け、和訳やカタカナ表記が定着した技術用語は日本語で書く。コード識別子、プロダクト名、略語は原文のまま使う
- 日本語と英数字の境界には半角スペースを入れる
- 日本語文の句読点は「、」「。」を使う（半角の `,` `.` は使わない）
- 文章としての正しさ（表記、語彙、構成）は japanese-tech-writing スキルをリファレンスとする

## 開発ワークフロー

- 探索→計画→実装→コミットの順で進める。変更前に必ず既存コードを読んで理解する
- GitHub Flow を使用する。メインブランチは main
- すべてのタスクをタスク管理ツール（TodoWrite / TaskCreate）で管理する
- 独立した複数の操作は、関連するツールを同時に呼び出して並列実行する
- 複雑な問題の検証にはサブエージェントを使用する
- テストは t-wada のメソッドに従う。テストに合格することではなく、問題の要件を満たすことを目的とする

## プログラミング原則

- **KISS**：動作する最も単純な設計を選び、早すぎる最適化を避ける
- **YAGNI**：現時点で必要のない機能や抽象化を先回りして作らない
- **DRY**：同じ知識やロジックを複数箇所に重複させない
- **Rule of Three**：重複の抽象化は 3 回目の出現まで待ち、DRY の早すぎる適用を防ぐ
- **SOLID**：単一責任、開放閉鎖、リスコフ置換、インターフェース分離、依存性逆転に従う
- **高凝集・低結合**：モジュール内は密に、モジュール間は疎に保つ
- **関心の分離**：異なる責務は異なるモジュールに分ける
- **SLAP**：1 つの関数内では抽象度を揃え、高レベルと低レベルの処理を混在させない
- **継承より合成**：振る舞いの再利用は継承ではなく合成で実現する
- **Tell, Don't Ask**：オブジェクトの状態を取り出して外部で判断せず、オブジェクト自身に振る舞いを命じる
- **デメテルの法則**：直接の協力者とだけ対話し、`a.getB().getC()` のような連鎖呼び出しを避ける
- **CQS**：メソッドは状態を変えるコマンドか、値を返すクエリのどちらかに限定する
- **Fail Fast**：異常は早期に検出して明示的に失敗させ、エラーを握り潰さない
- **最小驚きの原則**：読み手が予想したとおりに振る舞うコードと API を書く
- **Boy Scout Rule**：担当した変更の範囲内で、コードを来た時より綺麗にする（範囲外の独断リファクタはしない）

## コーディング規約

- コメントは日本語の「だ・である調」で書く
- 命名規則は一貫させる

## コミット規約

- Conventional Commits v1.0.0 (https://www.conventionalcommits.org/en/v1.0.0/) に準拠する
- subject は「type: 日本語の要約」の 1 行のみで書く（type は英語、要約は日本語）
- body は書かない。詳細は PR の description に記載する
- `type(scope):` の scope 記法は使わない（`type:` のみ）
- プロジェクト側に独自の規約（commitlint 設定、プロジェクトの CLAUDE.md やメモリ）がある場合はそちらを優先する

## Git 安全規則

- `.gitignore` で除外されたファイルを git 管理に追加しない。gitignore を一時的に書き換えて追加する迂回も行わない
- 履歴から削除したユーザー名や機密情報を、PR コメントや commit message など公開される文脈に再び書かない。「ユーザー名」「該当文字列」のような generic な表現で言及する

## Discord 応対

- Discord 経由（`<channel source="...">` タグ付き）のメッセージへの応答は、必ず Discord の reply ツールで送る。ターミナルへのテキスト出力は相手に届かない
- Discord への返信で Markdown のテーブル記法を使わない（レンダリングされない）。箇条書き、段落、コードブロックで代替する
- Discord 経由の作業では AskUserQuestion などの CLI 確認ダイアログを出さず、確認や承認は Discord の reply で取る。これは承認手順の省略を意味しない

## 設計ドキュメント

- superpowers 系スキル（brainstorming、writing-plans など）で作成した spec、design、plan のドキュメントは、ユーザーの明示的な指示がない限り git に commit しない（`docs/superpowers/` 配下はグローバル gitignore で除外済み）。要点はメモリに集約する
