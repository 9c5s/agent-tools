# メモリメンテナンス

Claude Code のプロジェクトメモリ (`~/.claude/projects/<スラッグ>/memory/`) を横断的に保守する。
lint が答えるのは「構造が正しいか」、inventory が答えるのは「何が書いてあり、まだ正しいか」である。promote と prune はその結果に基づく整理の実行を担う。

## モード判定

引数 `$ARGUMENTS` の先頭語でモードを決める。続く引数はそのモードのオプションとして扱う。

| 引数 | 動作 |
|---|---|
| (なし) または `lint` | 全プロジェクトを機械検査する |
| `lint <スラッグ>` | 単一プロジェクトを機械検査する |
| `inventory` | 棚卸しレポートを生成する |
| `promote` | 共通規範のグローバル昇格を提案する |
| `prune <パス>...` | 指定メモリを削除する |

## 前提知識

- 各プロジェクトのメモリは「1 ファイル 1 事実」の個別ファイルと、1 行ポインタ index (MEMORY.md) で構成される
- 個別ファイルの正規形式は次のとおり:

```markdown
---
name: <kebab-case スラッグ>
description: <1 行要約。「|」「:」等を含む場合は二重引用符で囲む>
metadata:
  node_type: memory
  type: <user | feedback | project | reference>
  originSessionId: <任意>
---

<本文>
```

- MEMORY.md は毎セッション全文ロードされるため、「`- [タイトル](file.md) — フック`」形式の行と見出しだけで構成し、知識本文を直書きしない

## lint モード

スキルのベースディレクトリを `<base>` として、次を実行する:

```bash
uv run "<base>/scripts/memory_lint.py" [--project <スラッグ>]
```

- 検査項目: index 双方向整合 (E1/E2)、frontmatter の存在と YAML 妥当性 (E3/E4)、正規形式 (E5)、wikilink 解決 (W1)、プロジェクト間の同名ファイル (W2)、MEMORY.md への直書き (W3)、サイズ閾値 (W4)
- 終了コード: 0 = エラーなし (警告のみ)、1 = エラーあり、2 = projects ディレクトリ不明

手順:

1. スクリプトを実行し、レポートをそのまま提示する
2. エラーには修正案を添える。警告は事実として報告し、対応の要否はユーザーに委ねる。警告には意図的な状態 (将来書く予定の wikilink、保持を決めた重複) が含まれるため、機械的に潰さない
3. 修正を依頼されたら Write / Edit ツールで直接行う。ファイルの削除だけは prune モードを使う

## inventory モード (棚卸し)

全メモリを読解し、内容ベースの棚卸しレポートを作る。

1. 先に lint を実行し、構造上の問題を把握する
2. Glob で全メモリファイルを列挙し、general-purpose サブエージェントに分担させて全件読解する。1 体あたり 30 ファイル程度を目安にする (読解と報告を合わせて 1 体のコンテキストに無理なく収まる分量)
3. 各エージェントには事実の報告だけをさせ、削除や統合の推奨は書かせない。対応の判断は棚卸しの利用者が行うものであり、レポートに判断が混ざると事実の把握という価値が濁るためである。報告項目:
   - ファイルごと: frontmatter の type、description の原文、本文要旨 (1〜2 文)、陳腐化リスク (特定バージョン、ブランチ状態、日付、ローカルパスへの依存)
   - ディレクトリごと: MEMORY.md との整合性
4. 結果を統合し、次の構成でレポートを作成する。ファイルに保存してユーザーに提示する:

```markdown
# メモリ棚卸しレポート
## 全体サマリ (プロジェクト数、ファイル数、分布)
## 横断的な所見 (index 不整合、プロジェクト間の重複、形式のばらつき、記述の食い違い、状態依存で陳腐化するメモリ)
## プロジェクト別詳細
```

## promote モード (グローバル昇格)

同趣旨の規範が複数プロジェクトに散在していると、新しいプロジェクトには効かず、文言も少しずつ食い違っていく。グローバル CLAUDE.md へ昇格して一元化する。

1. inventory の結果 (なければ lint の W2 と feedback 型メモリの description 比較) から、複数プロジェクトで同趣旨の規範を抽出する
2. 昇格前にハーネス設定を裏取りする。settings.json (attribution、permissions.deny) で既に強制されている規範は、CLAUDE.md に書いても毎セッションのコンテキストを消費するだけなので書かない
3. 昇格候補ごとに次の 3 点を提示し、承認を得る:
   - 昇格する文言案と挿入先セクション
   - 昇格により用済みになる各プロジェクトのメモリ一覧
   - 昇格せず残すプロジェクト固有の例外 (プロジェクト側の規約が優先される旨を文言に含める)
4. グローバル CLAUDE.md の実体を確認して編集する。symlink の場合は実体側のリポジトリで branch を切り、適切な粒度で commit する。push と PR 作成はユーザーの指示を待つ
5. 昇格が確定したら、用済みメモリの削除を prune モードで提案する

## prune モード (削除)

メモリの削除は復元できない。そのため「一覧提示 → 承認 → 削除 → 検証」の順を崩さない。

1. 削除対象の一覧と削除理由を提示し、ユーザーの承認を得る
2. 承認後に次を実行する。対象ファイルの削除と、MEMORY.md からの該当 index 行の除去をスクリプトがまとめて行う:

```bash
uv run "<base>/scripts/memory_lint.py" --prune <ファイルの絶対パス>...
```

3. lint を再実行し、index 整合が保たれていることを確認して報告する

スクリプトは MEMORY.md 自体とメモリディレクトリ外のパスを拒否する。シェルの削除コマンド (`Remove-Item` / `rm`) は permissions.deny で拒否されるため使わない。
